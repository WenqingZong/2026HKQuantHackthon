# 2026 HK Quant Hackathon — ETF 因子与机器学习流水线

这是队伍里 **zwq 负责的模型部分**：从 Databento 拉原始行情 → 计算 Alpha101 因子 → 训练
MLP / XGBoost / LightGBM → 用 Rank IC 和 top-k 等权回测评估。

现在用的还是团队 ETF 池（`selected_etfs/`）加上 17 个只依赖日频 OHLCV 的 Alpha101 因子，
目的是**先把流水线跑通、把每个环节的接口定下来**。等因子清单定了，改一下
`config/default.yaml` 里的 `dataset.alphas` 就能直接正式训练，模型代码不用动。

## 目录结构

```

hkq/

  corporate_actions.py    # 分红/拆股复权（yfinance），把原始价还原成总收益序列
  alphas.py               # Alpha101 因子实现与注册表
  dataset.py              # 因子 + 标签 -> (date, symbol) 长表，时间切分
  models.py               # MLP / XGBoost / LightGBM，统一 fit / predict 接口
  ic.py                   # Rank IC 与逐因子 IC 表
  portfolio.py            # 日频组合回测、成本计提、绩效与成本敏感度
  report.py               # 产物落盘：JSON 元数据与 markdown 训练报告
  pipeline.py             # 把上面几步串起来的下载 / 特征 / 训练流程
  config.py               # YAML 配置的解析
main.py                   # 命令行入口（--log-level 控制日志级别）
tests/                    # 因子公式、标签对齐、时间切分、成本口径、报告格式、模型接口的校验
selected_etfs/            # 团队筛出来的训练池与交易池（含字段的完整表）
example_databento_data/   # 官方给的一份样例数据，可以对照字段
data/                     # 行情与因子数据集（git 忽略）
artifacts/                # 训练结果与报告（git 忽略）
```

## 快速开始

```powershell
uv sync                     # 装依赖（torch 走 pytorch-cu130 源，5090 可以直接用）
```

Databento 的 key 放在仓库根目录的 `.env` 里（这个文件不进 git）：

```
DATABENTO_API_KEY=db-xxxxxxxx
```

然后按顺序跑：

```powershell
uv run python main.py download   # 下载训练池 + 交易池的日频行情，约 10 秒、花费约 0.2 美元
uv run python main.py features   # 算因子、生成数据集，约 10 秒
uv run python main.py train      # 训练三个模型并评估，CPU/GPU 都不到 1 分钟
uv run python main.py all        # 上面三步一起跑
```

单独跑某个模型、换配置文件：

```powershell
uv run python main.py --config config/default.yaml train --models xgboost
```

提交前的检查：

```powershell
uv run python -m pytest tests -q
uv run ruff check . ; uv run ruff format --check .
uv run mypy
```

## 数据

### 数据源怎么选的

比赛给的是 Databento 历史数据接口。日频策略只要 OHLCV，但不同数据集差别不小：

| 数据集 | 起始日期 | 覆盖 | 适合 |
| --- | --- | --- | --- |
| `EQUS.SUMMARY` | 2024-07-01 | 合并全市场成交，每个代码每天**一条**记录，成交量是全市场的 | 成交量最准，但历史最短 |
| `EQUS.MINI`（当前） | 2023-03-28 | 价格是合并后的完整行情，成交量只含部分交易场所（约为真实值的 3–8%，比例还会漂移） | 历史多 50% |
| `DBEQ.BASIC` | 2023-03-28 | 每个交易场所各一条记录，需要用成交量加权合并 | 需要更长历史 + 分场所明细 |

当前用 `EQUS.MINI`：876 个交易日 vs SUMMARY 的 559 个。代价是成交量只有部分场所，
但 Alpha158 的成交量类特征（VMA / WVMA / CORR 等）大多是比率或相关系数，对整体缩放不敏感，
而且比例漂移是缓慢的。两个数据集**不能拼**——拼接处成交量会跳 25 倍。

> ⚠️ **本轮复权只有拆股、没有分红。** yfinance 在重拉 2023 年起的分红时被限流封死
> （单只也 403），只能退回到「从价格跳空反推拆股」的兜底（`splits_from_price_jumps`，
> 检测到 17 个拆股事件）。除息日的价格下跌因此仍然是未复权的，高股息 ETF 会有一点系统性低估。
> 等 yfinance 恢复后重跑 `main.py download` 就能补上，之后 features/train 不用改任何东西。

想换数据集只改 `config/default.yaml` 的 `data.dataset` 和 `data.start`。
`hkq/data.py` 里已经处理了"同一交易日多条记录"的情况：开盘/收盘取成交量最大场所的价格，
最高/最低取各场所极值，成交量求和，所以换成 `DBEQ.BASIC` 也能直接跑。

### 下载了什么

- 代码池 = 训练池（`training_tickers.csv`，172 只）∪ 交易池（`trading_tickers.csv`，176 只）= **182 只**；
  训练用训练池，交易池先一起下下来备用。
- 字段：`date, symbol, open, high, low, close, volume`，落在 `data/raw/bars_daily.parquet`。
- 每次下载会把查询参数、行数、数据质量降级的日期写进 `bars_daily.manifest.json`。
  当前有 3 天是 Databento 标记的 degraded（2025-12-15、2026-01-12、2026-08-31），做归因时留意。
- 要分钟级数据，把 `data.schema` 改成 `ohlcv-1m` 即可，时间戳会自动换算成纽约时间再归日；
  但一年多的分钟数据量很大，先想清楚用不用得上。

### 分红与拆股（复权）

Databento 给的是**未经复权的原始成交价**：除息日价格会自然下跌，拆股日价格按比例缩水。
不复权的话，标签会把分红当成亏损，拆股更会变成一根 -67% 的假 K 线——样本期内 SCHD、
SCHP、XLE/XLK/XLB/XLU/XLY、PALL、PPLT、ZCSH、ETHA 都拆过股，SCHD 那天原始价格从
84.62 掉到 28.54。

所以 `download` 会顺带用 yfinance 拉一份分红与拆股记录（`data/raw/corporate_actions.parquet`），
`hkq/corporate_actions.py` 据此算出复权因子：`复权价 = 原始价 × f`，事件日满足
`f_t / f_{t-1} = 拆股比例 + 每股分红 / 收盘价`，这样 `adj_t / adj_{t-1} - 1` 就是含分红再投资的
真实收益。成交量按拆股因子倒数调整，保持「量 × 价」不变。

**但复权因子必须是因果的。** 教科书式的做法是算完累积因子再除以最后一天（后复权），
这样所有价格都在「今天」的单位下、跨期可比；代价是 t 日的价格水平依赖 t 之后发生的所有
分红和拆股——那就是未来函数。样本期内 2024-08-01 就有 24 只 ETF 的「未来缩放」偏离超过 10%
（PPLT 0.10、ETHA 3.00），而 17 个因子里有 8 个用价格差构造、对尺度敏感。

所以这里分成两条路：

- **收益率 / 标签**用因果复权（只用当日及之前的事件），归一化常数反正会在比值里抵消；
- **因子**走 `point_in_time_panels`：逐日把最近 25 个交易日缩放到「以当日为止」的价格单位，
  当天算出来的因子和当天能看到的信息完全对应。

代价是建特征要跑 585 次滚动窗口（约 80 秒），换来的是任何日期的因子都不含未来信息——
`tests/test_leakage.py` 里有一条回归测试专门盯着这件事：在 cut 之后补一次拆股，cut 之前
的特征和标签必须一字不差。

复权后如果还有单日涨跌超过 35% 的记录，会打一条 warning——那通常意味着 yfinance 漏了事件。

## 因子

一共 **186 个**：78 个 Alpha101（`hkq/alphas.py`）+ 111 个 Alpha158（`hkq/alpha158.py`）
− 3 组重复各去掉一个（`alpha033≡-KMID`、`alpha101≡KMID2`、`alpha054≡-KSFT2`，
保留 Alpha101 那一侧）。

- Alpha101 全部 78 个都实现了；需要 vwap 的用 **HLC3 代理**、需要 advN 的用 **N 日平均美元成交额**，
  和 psq 相关性包的口径一致；原文里的分数窗口（如 12.7054）取整。
- Alpha158 按 Qlib 定义实现（9 个 K 线形态 + 4 个价格位置 + 5/10/20/30/60 五个窗口的滚动统计），
  只注册 psq 那份相关性包里实际出现的 111 个列名。

因子和标签都从**因果复权**后的价格上算：只用当日及之前的分红/拆股，不含未来事件
（`tests/test_leakage.py` 有一条回归测试盯着这件事）。

> 代价：价格水平停在「各标的自身累计口径」上，拆过股的标的和没拆过的比差一个固定倍数。
> 对收益率、比率类因子没有影响；对价格差类因子是跨标的口径差异（不是未来信息）。
> 之前那版逐日 point-in-time 窗口能消掉这个差异，但 186 个因子、最长 250 日回看会让
> 建特征从 20 秒变成几小时，所以退回到因果复权。

## 数据集

`hkq/dataset.py` 把宽表拼成 `(date, symbol)` 的长表，每一步都有明确的时间约束：

1. **标签**：`lag=1`、`horizon=5` —— 因子用当日收盘价算出来，最早只能下一个交易日成交，
   所以标签是"第 t+1 日进场、持有 5 个交易日"的收益。不做这个滞后等于自带前视偏差。
2. **标签标准化**：默认按日做横截面 `rank`。一是把回归变成排序，和"选前 k 只"的目标一致；
   二是去掉市场整体涨跌（beta），模型不用花容量去拟合"今天大盘涨不涨"。
   这一步是纯单调变换，不影响 Rank IC 的数值。
3. **因子标准化**：同样按日做横截面 `rank`，映射到 `[-0.5, 0.5]`，缺失值填 0（中性）。
   这样树模型和 MLP 都不用再套一层 scaler，也不会有跨期泄漏。
4. **预热期**：前 20 个交易日只用来把滚动窗口填满，不参与训练。
5. **切分**：train 2024-08-01 ~ 2025-06-30、valid 2025-07-01 ~ 2026-01-31、
   test 2026-02-01 ~ 2026-10-27，严格按时间前后切，不交叉。

## 模型

三个模型对外只有 `fit(X, y, X_valid, y_valid)` 和 `predict(X)` 两个方法，
在 `hkq/models.py` 的 `build_model` 里注册：

- **XGBoost / LightGBM**：回归未来收益，验证集早停。
- **MLP**：PyTorch，默认 `[128, 64]` + Dropout 0.2，AdamW，验证集损失早停，自动用 GPU。

加第四个模型（比如 LightGBM 的排序目标、或者 LSTM）只要实现这两个方法，再在
`build_model` 里加一行分支。

> 早停说明：标签噪声很大（5 日收益的信噪比本来就低），所以 MSE 早停在几十棵树的量级就停了。
> 换成 `label_norm: rank` 之后明显改善（XGBoost 35 棵 vs 5 棵，预测值也不再挤成几个值）。
> 想继续调就动 `models.*` 的参数和 `train.early_stopping_rounds`。

## 评估

- **Rank IC**：每个交易日算一次预测值与未来收益的 Spearman 相关，再看均值、ICIR、
  胜率、t 值。这是判断"模型有没有选股能力"最直接的指标。
- **top-k 回测**：逐日盯市的组合模拟。信号日 t 出预测，第 t+1 个交易日收盘成交（和标签的
  `label_lag` 对齐）；建仓时等权买入前 10 只，之后**只有进出的标的才交易**，留在组合里的
  标的权重随涨跌自然漂移、不重新等权。基准是期初等权买入全池后不再调仓、不计成本。
  同分的股票会先随机打散，避免默认按代码字母序选股。
- 每次训练还会输出**逐因子**的 Rank IC 表（`artifacts/alpha_ic.csv`），
  后面 psq 做因子筛选、以及看哪类因子在这个池子里真正有效时可以直接用。

**交易成本**：账户佣金实测约 0.4–0.7 bp/边，加上滑点，`backtest.cost_bps` 先设 **1.5 bp**。
计提方式是 `net = (1 + gross) × (1 − Σ|Δw| × bps / 1e4) − 1`：

- `Σ|Δw|` 是当期成交的**名义金额**，卖出和买入都算进去，所以乘的是一个单边费率；
  空仓建仓只成交一次 100%，不会把现金的变化重复计一遍。
- 换手仍然按 `0.5 × Σ|Δw|` 报告（当前约 0.9/次），年化拖累约 0.7%。
- 报告里附**成本敏感度表**（默认成本的 0/1/2/4/8 倍，即 0 / 1.5 / 3 / 6 / 12 bp），可以直接看出策略能承受多高的摩擦。
- 口径上的偏差：所有 ETF 统一用同一个费率，而池子里 FXF / FXB / CMBS 这类
  日均成交额只有 200–400 万美元的标的，1.5 bp 明显偏乐观；基准是**不计成本**的。

## 当前结果

`main.py train`，876 个交易日（训练 2023-05 ~ 2025-06），测试集 182 个交易日，含 1.5bp 单边成本：

| model | valid IC | test IC | test CAGR | Sharpe | 最大回撤 | 换手 |
| --- | --- | --- | --- | --- | --- | --- |
| xgboost（depth 5, 1500 棵） | 0.076 | **+0.019** | 38.3% | 1.68 | -11.5% | 0.81 |
| lightgbm（31 leaves） | 0.065 | **+0.013** | 21.5% | 0.97 | -10.1% | 0.80 |
| mlp（2048-1024-512） | 0.089 | **+0.004** | 23.5% | 0.85 | -15.9% | 0.71 |
| 全池等权买入持有 | — | — | 6.1% | — | — | — |

对比上一版（559 天、小模型）：**测试集 IC 从 0 附近变成全为正**，`scripts/sweep_models.py`
的 14 组配置里 13 组测试集 IC > 0。加历史（+54% 样本）比调模型本身贡献更大。

但要清醒：测试集 IC 只有 0.004–0.019，`38%` 的年化来自 182 个交易日、37 次调仓，
仍然有明显运气成分；三个模型之间 21%~38% 的差距不能当成模型优劣的证据。

## 已知限制 / 下一步

1. **历史太短**：合并行情只有 2024-07 之后。要更长历史得混入 `EQUS.MINI`，
   或者只对价格类因子用单场所数据——需要团队先定口径。
2. **只有单次切分**：还没做滚动重训（walk-forward）。现在训练一次用到 2025-06，
   实际交易时应该按周或按月往后滚，这部分接口已经留好了（`split.ranges()`）。
3. **因子是临时选的**：等 psq 的因子库和筛选标准出来，替换 `dataset.alphas` 即可。
4. **持仓重叠**：ETF 池去重后仍会有重叠暴露，可以在 `dataset.py` 后面加一步
   按 `overlap_family` 做组内约束，或者在组合层面限制单方向权重。
5. **风控没接**：回测里只有交易成本，没有止损、没有波动率目标、没有仓位上限，
   这部分要等 zy 的方案。
6. **执行假设**：回测假设按收盘价全额成交，既没有按 ADV 算冲击成本，也没有部分成交和
   成交概率。日均成交额中位数在 1 亿美元以上，几百万的仓位影响不大，但仓位一放大
   就得换成带冲击模型的执行假设。
7. **换手降不下来**：虽然已经改成「不重新等权、只交易进出场」，但模型每 5 天挑出来的
   10 只与前一期平均只重合 0.9 只，所以换手仍然是 0.9/次。想真正降换手得从信号端入手
   （拉长 horizon、加换手惩罚、设持仓缓冲带），不是回测端能解决的。也正因为换手高，
   每期新进场的标的有 9 只左右，单只权重自然落在 1/top_k 附近；代码里已经加了
   「新进场最多拿 1/top_k、其余留现金」的封顶，避免换手降下来以后单票被灌成重仓。
8. **分红/拆股依赖 yfinance**：这是个非官方接口，拉不到就复权不了。复权后仍有异常跳空会
   打 warning，但不会自动修正——真实交易前要人工核对一遍。
9. **PIT 滚动窗是定长的**：现在是 25 个交易日（= `min_history` + 5）。以后加回看更长的因子，
   必须同步把 `min_history` 调大，否则窗口头部会被截断，算出来的因子是错的（不是泄漏，是错）。
